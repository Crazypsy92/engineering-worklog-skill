# Daily Review｜每日工作与生活复盘

## 目标与适用范围

这是**个人每日复盘 Skill**，不是企业报工表。面对一整天的聊天记录、日志、手写笔记、Codex 任务、科研实验、个人体验、阅读感想与生活琐事，产出**可回看、可复盘、可跟进**的记录。

与仓库根目录的 `engineering-worklog` 区分：

- `engineering-worklog`：上班前/下班前企业表单，固定字段、数量、工时、逐项完成百分比。
- `daily-review`：全天复盘，兼顾**工作、学习、个人事务、感受和思考**；不强制工时，不强制每项百分比，默认更重过程、问题、结果和后续。
- 如果用户同时要两份，先独立生成全天总结，再把其中经过证实且属于工作的事项压缩为表单字段，避免把个人事项混进公司工时。

## 输入与边界

接受用户原始碎片：“今天问了什么、安排了什么、试了什么、做成/没做成什么”、聊天历史、日报、截图、Markdown、日志和附件。用户声明的日期优先于设备时区或系统日期；`2026/11/11星期三`作为用户指定日期，不自动改成当前日期。

将每条信息标为至少一种事实状态：
- **已确认完成**：有运行/验收证据，或用户明确说“做完/测试通过/交付了”。
- **已尝试，结果有限/失败**：有运行证据，但未达到目标；如“抓到了但未离箱”。
- **已讨论/已布置任务**：出现“帮我、你给任务、能否、要不要、安排、准备”；不得写成“已经开发/已经修好”。
- **学习/理解/提出疑问**：概念探讨、论文、技能、文学，允许记录形成的认识；不得写成实验结果。
- **待核实**：记录不足、来源冲突、效果未知、无法验证。

**最重要的防错规则：用户给另一位助手的命令不等于执行成功。** 例如“移植驱动并编译”只说明提出了移植/验证需求，除非另有编译日志，不能说“完成驱动移植与编译”。

内容合并：同一项目连续多轮任务—追问—改方案—测试—反馈，只保留一次完整叙事，并写出**目标为何变化、遇到的问题、如何处理、最终走到哪一步**。不要把每句话都当作新任务；不要把多个测试版本相加成独立成功次数。

## 分类规则

按当天的实际内容灵活使用，空栏目不强行出现：

1. **工作 / 项目研发**：产品研发、测试、机械臂、视觉、嵌入式、代码、交付与领导工作事项；用户明确划入“工作”的内容保持原归类。
2. **学习 / 研究**：硕士论文、文献、技术原理、算法理解、课程、学习材料。
3. **个人 / 生活**：个人计划、日常生活、兴趣爱好、读书影视、个人成长与观点；**个人思考和生活事件分开**，不要从一条抱怨推断心理状态。
4. **工具 / 杂项**：ChatGPT 界面、Obsidian、软件配置、设备工具，除非用户认为是某研发项目的一部分。
5. **个人项目**：像业余嵌入式驱动这样的活动，若用户未说明是否属于工作，可以记为“个人研发/技术实践”，不要自行假定劳动关系。

若原始笔记标为“杂项”，优先按真实主题拆分，不必全部堆在杂项里。用户特意要求保留某个原始分类时照办。

## 总结流程

### 阶段 A：构建事件表（先在内部完成）

每件事提取 `主题 | 动机/目标 | 实际操作或提问 | 遇到的阻碍 | 处理方式 | 证据与结果 | 状态 | 下一步`。

- 对于已验证的实验，保留必要数字和**数字含义**（如6/6夹中但0/6离地；受控18/18≠现场定位100%）。
- 对于尚未完成的任务，明确写“安排/计划/等待实测”，不写“完成100%”。
- 对于用户表示“不关心后续稳定性”的边界，按阶段目标阐述，不反复拿未来长期性能要求否定眼前阶段成果。
- 对于没有生活素材的日期，写“本日未记录具体生活事项”，不编造吃饭、睡眠、运动、心情。

### 阶段 B：输出结构（默认：标准版）

最高 `#` 仅用于整篇日期标题，章节使用 `##`。以用户惯用的 Obsidian Markdown 为主；标题跳转使用 `[[#章节标题|显示文字]]`，需要目录时生成。

```markdown
# YYYY/MM/DD星期X

## 今日事宜
| 类别 | 今日推进 | 状态 |
| --- | --- | --- |
| 工作 | ... | 已验证 / 部分完成 |
| 学习 | ... | 已讨论 |
| 个人 | ... | 已记录 |

## 工作与项目
### 可选：仅在用户要求更深层分层时使用，不必默认出现
| 主题 | 做了什么 | 结果/证据 |
| --- | --- | --- |
| ... | ... | ... |

## 学习与研究
...

## 个人与生活
...

## 问题、处理与结论
| 问题 | 排查/处理 | 结果或剩余限制 |
| --- | --- | --- |
| ... | ... | ... |

## 未完成与后续
| 优先级 | 后续动作 | 验收依据 |
| --- | --- | --- |
| ... | ... | ... |

## 今日回顾
...
```

上面是**素材充分时的完整版框架**，不是每次必须出现所有标题。默认“今日事宜”放最前；工作/学习/个人按话题合并；记录顺序大致遵循一天推进过程；**日末回顾放最后**。

如果用户偏好表格，优先用表格描述事实与问题；长段技术细节可以放在表格后，避免大表宽度过宽。AI 问答**按主题合并**，不逐条复制问句或逐条添加时间戳；回答价值是澄清了什么/还要测什么。

### 阶段 C：输出深度

- **速览**：200–450中文字符，主要事项、问题和下一步。
- **标准（默认）**：约700–1600中文字符，表格为主，兼顾项目和个人，不强求写满。
- **深度复盘**：用户要求“详细/完整/别漏”时，按项目解释背景、过程、对照、失败、解决办法、证据、下步，并附个人感受与知识收获；可达到更长篇幅。
- **仅工作/仅个人**：只输出请求部分，其他不插入。

偏好**高保真而非机械缩写**。个人观点保留原意和语气，不能替用户擅自下心理学结论；没有提供心情就不要自动写“今天很充实/很焦虑”。

## 事实与数字的约束

- 验证层级分开：`计划 → 已执行 → 实验达标 → 完整功能通过 → 真实设备验收`。
- “修改了代码”不等于“完成实跑复验”；“能抓住/短提”不等于“稳定搬运/货架放置”；“有点云清理”不等于“现场地图对齐”。
- **时间范围要明确**：当天复用的旧数据、当天新采集、当天新运行、历史基线必须分开；不能把不同工况的成功率相加。
- 每个结论优先给两部分：**观察到什么**，**目前能证实到哪一步**。
- 数量有单位和分母。若用户要求完成百分比，仅在分母或用户明确确认的情况下写；**每日复盘默认不硬塞百分比**（报工 Skill 才逐项强制）。
- 用户的日期、星期和实际记录互相矛盾时，保留原始日期并标注需核对；不要自行搬动活动到别的日期。
- 文献与学习：明确“今天讨论了什么、主要认知、留下什么问题”，不将理论分析写成个人实现。

## 个人事项处理与隐私

- 用户的情绪、反思、阅读、家庭、身体、理财或私人计划，可以写在私人的日报中，**不公开上传到代码仓库**。
- 本仓库是公开代码仓库；只允许上传通用 Skill、匿名化虚构示例与空模板。**任何真实日记、姓名、公司资料、个人健康信息或非公开工作材料，未经明确授权不得推送到公共仓库**。
- 提供了私人信息时，可以在当前对话返回私用 Markdown 日记，必要时写到用户指定的私人本地路径；不要混入公司日报或公开模板。
- 允许记下“今天提出了什么问题、纠正了什么误解、形成什么判断”；不得评价用户人格。

## 质量检查

1. 是否覆盖用户明确提到的所有重要主题，包括工作外事项？
2. 提交任务/讨论/计划是否被误写成已完成？能否在原话或文件找到完成证据？
3. 今天新增动作与历史数据是否区分？
4. 问题—处理—结果—遗留是否闭环？
5. 实验数字、场景、成功判据是否对齐？
6. 是否把“个人想法/体会”自然放入，而不是只产出KPI？
7. 是否符合用户偏好的中文正文、英文文件名、Obsidian 标题跳转、今日事宜置顶与日末回顾置后？
8. 公共仓库里是否只保留通用能力与**虚构**示例？
